# Key actors by worker and user id

An actor is a user id together with the worker that recorded it. Each worker of a parallel test run has its own application database, so the same id is a different user in each. The user directory was keyed by id alone, so the last worker to write won the name, `overview` counted about a third of the users that had signed in, and `actor` showed one person's name over the work of several. The directory row now carries the worker of the process that saw the user, a record's user is matched with its worker, and every count of signed-in actors counts the distinct pairs. This amends ADR 0007 only in what "the recorded user" is keyed by: the links, and the rule that nothing is inferred, stay as they are.

A store per worker would remove the collision, but it splits one run across files, and every question about the run would then need every file. A blind spot that says ids may collide would leave `actor` showing one name over several people's work, and would make every count of actors a lower bound instead of a count.

`actor` takes `worker`, and `occurrences` takes it beside `user_id`. A call that names a worker reads only that worker's people. A call that names none reads the people of no worker first at each stage of identification and decides on them when the stage finds any. It reads across workers only when the stage finds none there, and an id that several workers hold is then several candidates, each with its worker, and the answer offers a call that reads one alone for up to five of them, the most next calls an answer carries. So a store that holds no parallel run answers as before, a person of no worker whom the user directory holds is reached by id alone, and a person of a worker by id and worker. Reading the people of no worker through every stage before any worker's would also reach an id that only records hold, but a name that merely contains the text would then decide before an exact id among a worker's people. The cost of the order chosen is that such an id, held by no worker in the records alone and by a worker in the directory, resolves to the worker's person. An id read without `worker` can still stand for several actors: `actor` decides on one person while workers hold the same id, and `occurrences` lists the records of all of them in rows that do not show the worker. Both then add a note that says how many workers hold the id, where no worker counts as one. A sentinel value that means "no worker" on the argument would reach the same person, and would be one more value to explain and to keep out of the tokens a runner can give.

The worker is null outside a parallel run, on the directory row as on the record (ADR 0017). A composite primary key would need `worker NOT NULL DEFAULT ''`, and the directory would then disagree with `records.worker` on what no worker is. The directory is instead unique on an expression index over the id and `coalesce(worker, '')`, which the upsert names as its conflict target. A person carries `worker` in an answer only when they have one, so no answer changes its shape outside a parallel run.

The schema version goes to 5 and the store is rebuilt, not migrated.
