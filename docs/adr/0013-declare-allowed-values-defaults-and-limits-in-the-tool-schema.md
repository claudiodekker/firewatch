# Declare allowed values, defaults and limits in the tool schema

Each tool's input schema is the authority for what an argument accepts. A closed argument declares its values as the schema `enum`, an argument with a default declares it as `default`, and a bounded number declares `minimum` and `maximum`. The server reads these declarations back when it reads a call: `Arguments` takes the accepted cases, the range and the default from the tool's own schema, so what `tools/list` shows and what a refusal lists cannot disagree. Where the values that fit depend on the rest of the call, such as the measures of one type, the schema declares their union, built from the same per-type lists the reader checks. A few arguments keep a reader of their own that shares its source with the schema instead: `format` reads `AnswerFormat`, `detect`'s `shape` reads the shipped detectors, and `fingerprint`'s `repeat_seconds` reads its list of whole divisors of the minute. An argument's description carries only what the schema can't: what a value means, when it applies and what it excludes. It never lists the values again, and an argument whose name and schema say everything has no description.

This supersedes the tradeoff in #194, which kept the values in the descriptions and declared no new enums. The descriptions had to name every value then, so enums would have repeated those lists for about 1,500 characters under the 6,000-token listing cap. Moving the lists instead of repeating them costs about 150 characters. A client that validates against the schema, or constrains its calls to it, now sees the valid choices before the call, not from a refusal after it.

The alternative was a declaration object per argument passed to both the schema and the reader. Reading the schema back needs no new type, and it leaves the reader no other source to drift from. The cost is that the listing grows with every closed argument, and a value whose meaning needs words still spends them in the description.
