# Record a failed validation as the names of its invalid fields

A request that fails validation stores `invalid_fields`, the names of the fields that failed, and nothing else about the failure. Laravel never reports a `ValidationException`, so Nightwatch records no exception for it, and a form that fails is redirected back with the same 302 a successful submission gets. Laravel does attach the exception to the response it renders from it. Firewatch reads it there when `RequestHandled` fires, holds the field names, and pairs them to the request record Nightwatch writes when the request terminates. This is a second capture path beside query bindings, and a second field the wire never sends (ADR 0003).

The list is the state: a request failed validation when `invalid_fields` is not NULL, and no flag is stored beside it. Field names get the care a payload gets. The messages are left out because a message can quote the input, and the values because a payload is stored only for a 500. At most 100 entries are kept, each cut at 255 bytes, and the last one counts the names left out, because a rule on a list of rows fails once per row. A rule on a map the client keys, such as `invites.*`, names the key the client sent. NULL means no validation exception was rendered, which is not the same as valid: errors a controller returns by hand, a response that middleware replaced, and Livewire's own handling leave nothing to read. Every answer about requests carries the blind spot `unrendered-validation-failures`.

A failed validation is judged as answering at least 422, the status Laravel answers a client that asked for JSON, also when it answered a 302. One rule in `Failure` applies it to `failing-routes`, to the failure rate `rank` reports, and to the failed executions `trace` offers, so a route does not read as failing or healthy by the `Accept` header of its clients. A threshold of 500 leaves both forms out. Answers show the stored status, and `failing-routes` states how many of a route's failures were failed validations. The server-error and client-error shares of `overview` stay on the stored status, because they count status classes.

The alternatives were a flag alone, which tells less for the same capture, the redirect target of every redirect, which separates the two cases only when a failure redirects back, and keeping the payload for a failed validation, which stores what users typed into forms that were refused. A detector shape of its own was rejected too: a 422 would be reported by two shapes, and a test suite, which fails validation on purpose, would always have findings in it.
