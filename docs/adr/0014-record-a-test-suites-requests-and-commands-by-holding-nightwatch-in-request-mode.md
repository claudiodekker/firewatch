# Record a test suite's requests and commands by holding Nightwatch in request mode

Under `testing`, Firewatch records each request a feature test sends and each outermost command it runs as an execution of its own. Nightwatch picks request or command mode once, when its provider registers, and keeps one execution state for the application. Laravel raises no command events while running unit tests, and `$this->artisan()` never calls the console kernel's `terminate()`, so neither mode records a test's executions by itself. Firewatch therefore sets `NIGHTWATCH_FORCE_REQUEST` only around Nightwatch's registration, and starts each test application on a fresh trace with `NightwatchServiceProvider::flushState()`. It resets the state at each request with `Core::prepareForRequest()`, the reset Octane uses. For a command, it reroutes the console events and swaps a `CommandState` into `Core::$executionState`, with a copy of `Core::$sensor` whose `executionState` points at it, while the command runs. When the command finishes, it writes the command through Nightwatch's own `command()` and `finishExecution()`.

The HTTP kernel binds `request` twice for one request, and again for a request the application dispatches while it handles another. Firewatch therefore reads the call stack for the outermost kernel that handles a request, and resets only when that request is not the one whose execution is open. Nothing but the stack tells a request dispatched inside another from a request that follows one that threw out of the kernel, because Laravel raises no event when a request throws out of it. A request dispatched inside another stays part of the outer request, with no record of its own, which is what Nightwatch records in a served application. One case is left as Laravel has it. When the application also terminates the inner request, the kernel runs its lifecycle handlers for that request and not again for the outer one, so Nightwatch records the inner request in place of the outer one, in a served application too.

This widens the `@internal` Nightwatch surface `src` touches beyond `Core::$ingest` (ADR 0001). The guard follows that ADR. The wiring checks the state and the sensor property before it listens. Every listener reports a failure instead of throwing into the test. When Nightwatch's internals change, Firewatch reports it and the test run stops getting separate executions, but nothing throws into the suite. The switch, `capture.tests`, defaults to on, because a suite that captures under `testing` without it stores only fragments. The package's own suite turns it off, because it drives Nightwatch's modes itself.

The alternatives were a PHPUnit extension or a trait the application's tests use, which need changes to the application's tests, and leaving `testing` out of the default environments. The swap ties Firewatch to the shape of Nightwatch's execution states and sensor manager, so a Nightwatch release that reshapes them can turn test capture off until Firewatch follows. Commands Nightwatch handles as workers or schedulers are left alone, because their executions are job attempts and tasks, which this does not record.

Three rules keep a test run's store about the application. The migrations and seeders a test harness runs (`migrate:fresh` from `RefreshDatabase`, `db:seed`) run in a command state of their own and are dropped, even when one starts inside a request, because they would otherwise lead `overview` and `detect` with the database's setup. A test process's memory peak holds the runner and every earlier test, so Firewatch stores no peak for a test run's executions. What a test runs between its executions keeps its own execution id, but no source, stage or user, because Nightwatch would stamp it as request work of whoever signs in later. A test that runs `migrate` on purpose is left out with the harness.
