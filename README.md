# Firewatch

Firewatch is local telemetry for AI debugging: it captures what Laravel Nightwatch's sensors collect into a local SQLite file and lets an AI assistant query it over the Model Context Protocol. No dashboard; nothing leaves the machine.

## Install

Install is `composer require --dev claudiodekker/firewatch`:

```bash
composer require --dev claudiodekker/firewatch
```

## Connecting an assistant

An assistant's client starts Firewatch's MCP server with one launch command, run in the application's environment with the project root as working directory:

```bash
php artisan firewatch:server
```

In Claude Code that is `claude mcp add firewatch -- php artisan firewatch:server`. The server speaks MCP over stdio and exits when its input ends. It is a `firewatch:` process, so it is always Off and never captures its own reads, and it opens nothing in the store until a tool asks. Only `overview`, `rank` and `occurrences` exist so far. `overview` answers that no store has been written yet, that the store is unusable and why, that it holds no records, or how many records and requests it holds. `rank` is described below.

Every tool answers with one fixed envelope, in markdown by default, or in JSON with `format: json`, which carries the same information as structured content and as one compact text block. A `format` that is neither is refused; enumerated values such as `format` are matched exactly, never trimmed or lowercased. A failed call is a plain-text tool error, never an envelope, stack trace or path: `error: <code>`, one sentence naming the argument and value, then `argument:`, `accepted:` and `example:` lines. The codes are `missing_argument`, `invalid_argument`, `conflicting_arguments`, `unreadable_time`, `empty_window`, `split_outside_window`, `not_found`, `bad_cursor` and `internal`. An argument the tool does not take is refused with the arguments it takes: `invalid_argument` for one no tool takes (a misspelling), `conflicting_arguments` for one that belongs to another tool. A failure nobody expected is `internal` even with `app.debug` on, which never rethrows; it carries no argument lines, and the exception is reported once. The envelope always has the keys `tool`, `now`, `window`, `summary`, `empty`, `result`, `coverage`, `blind_spots`, `notes`, `truncated` and `next`, in that order, and `null` means not applicable, never unknown. `now` is the store clock in Unix seconds with microseconds, which goes back into a tool as a window bound. Markdown prints each line only when it applies: the tool and its summary, the window, the clock, the empty kind, the result, one `Store:` line, truncation, notes, blind spots and next calls. A list of same-shaped rows prints as a table, and a cell prints `null` as `n/a`, a boolean as `yes` or `no`, a list or object as compact JSON, with pipes escaped and line breaks flattened. An answer with nothing to show names why: `no_store`, `store_unusable`, `store_empty`, `window_empty` or `no_match`, the last two with the number of records they were drawn from, and its summary never says there are no problems. A summary is cut to 300 characters at a word boundary, and an answer carries at most five notes and five next calls. A tool reads one row beyond its `limit`, so exactly `limit` rows is a complete list and a cut by the limit is a `truncated` entry (`section`, `shown`, `matched`, `reason`, `how`; `matched` is `null` when counting would cost a second scan). A cell is cut at 2,000 characters on a character boundary and ends with `... [truncated, N characters]`, N being the characters cut; each section that had cells cut is stated once with reason `cap` and the number of cells in `shown`. An answer is kept under 24,000 characters (8,000 tokens at 3 characters a token, measured on the JSON in either format): over that, whole rows drop from the tail of the lowest-priority list, which is the last list of the result, then the one above it, and each cut list is stated with reason `size`. The first row of the first list, the summary, the blind spots, the notes and the next calls are never dropped. Windowed tools take `since` and `until`, read in the application timezone: epoch seconds (up to 4102444800), ISO 8601 with `Z` or an offset, a local date-time (`2026-09-30 14:00` or with a `T`) or date (midnight), a relative time (`-1d`, `-90 minutes`; units s, m, h, d, w, and `-1d` is exactly 24 hours), or `now`. Nothing else is read: `yesterday` and millisecond epochs are refused with `unreadable_time`. The window is half-open on `started_at`, a record at `since` is in and a record at `until` out, an absent bound is unbounded, and `since` not before `until` is refused with `empty_window`. Every window is anchored on the store clock, read once per call. `overview` is the first windowed tool; a window that holds none of the store's records answers `window_empty`. `coverage` carries the store's state (`ok`, `empty`, `absent` or `unusable`, with a `reason` when unusable), its record count and span, the record types the call read (`types_read`), the `history` (`from`, `reason` and the retention in `age_seconds` and `records`) and `straddling`, which only `compare` fills. The history is complete from the latest start among the types read: the store's creation, a clear, a clear of the type or the instant records were pruned through, whichever is latest. Every answer, empty ones included, carries the structural blind spots of the record types its call read, from a closed catalogue of eighteen ids with one sentence each (`blind_spots` lists `id`, `kind` and `message`), and a tool can't switch them off. After them come the condition blind spots, measured from the store on every call, each `kind: condition` with one sentence that has its facts inline and the same facts as fields (instants as Unix seconds): `history-pruned` and `history-cleared` (`from_at`, `reason`) when the window has no start or starts before the history the call read is complete from and that start is a prune or a clear; `store-rebuilt` (`rebuilt_at`, `why`: `schema` or `corrupt`) when the window starts before the store's last rebuild; `records-dropped` (`records`, `from_at`, `to_at`, `reason`) for the batches the store failed to keep inside the window, a lower bound read from `failures.jsonl` and the only statement that an answer may be incomplete; `drift` (`count`, `drift_kind`, `type`, `last_at`) for each kind of drift counted on a type the call read; `nightwatch-unverified` (`version`, `line`) while the latest batch came from a release above the verified line or a development build; and `redaction-active` (`headers`, `payload_fields`) when requests are read and either redact list is not empty. With both lists empty, Firewatch's default, nothing is attached. The Store line adds `history complete from <time> (<reason>); retention <age>, <records> records` once the history has a start.

The server starts only through `firewatch:server`. Firewatch registers no laravel/mcp handle, so never use `mcp:start` or `mcp:inspector` with it. To see what an assistant would get from `tools/list` without a session, run `php artisan firewatch:server --list`, or `--list --json` for the full descriptions and schemas.

Anything an application's providers print while the server boots goes to stderr, so it can't corrupt the protocol on stdout. Output printed before Firewatch's provider registers, from `bootstrap/app.php`, a config file or a package provider registered earlier, still reaches stdout and breaks the handshake. Run the launch command by hand to look for it; end with Ctrl-D.

## Modes

Firewatch decides once per process, when it registers, how it runs:

- **Stepped aside** when the environment is not in `environments`. It registers no command, listener or publish tag and writes no Nightwatch setting, so Nightwatch behaves as if Firewatch were absent. A console process reports this once; web processes stay silent. `Command "firewatch:doctor" is not defined` means the environment is not in `FIREWATCH_ENVIRONMENTS`.
- **Off** in a `firewatch:` command, when `enabled` is false, or when `ext-sqlite3` is missing or SQLite is older than 3.38.0. Nightwatch is disabled, its ingest is swapped for one that sends nothing, and nothing is captured.
- **Active** otherwise. Nightwatch is enabled and its ingest is swapped for Firewatch's, which writes what the sensors record into the store and sends nothing. A placeholder token and a loopback address nothing listens on stay behind it as a second guard.

Firewatch checks Nightwatch's ingest before it swaps it. If a Nightwatch release changed it, a console process reports that once and Nightwatch keeps its own ingest: disabled in Off, and in Active vetoed before every batch and pointed at the placeholder token and address.

Firewatch registers Nightwatch's provider itself, before Nightwatch reads its configuration. If something registered Nightwatch's provider before Firewatch's, such as another package's provider or a stale package manifest, a console process in Active or Off reports it once with the fix: remove the provider from your providers and run `php artisan package:discover`. In Active, a console process also reports once if the `IngestingEvents` event the veto listens on is missing. Neither report stops anything. Firewatch is verified against Nightwatch 1.30; a later minor or major, or a development build, still runs and is unverified.

In Active, every request, command, job and scheduled task is captured: Nightwatch's sample rates are set to 1, its `ignore_*` filters are off and its log level is `debug`, whatever the application configured. A `nightwatch` log channel the application defines itself keeps its own level. What you opt out of in code still stays out: `Nightwatch::ignore()`, `pause()`, `dontSample()`, `Sample::never()` and `Sample::rate()` on a route or a scheduled task, and every `reject*` callback. A job attempt follows the sampling of the execution that dispatched it. Exception frames always carry their source lines. When `deploy` is set it becomes Nightwatch's deployment; unset, Nightwatch resolves its own.

Logs on the default channel are captured without touching `LOG_STACK`. In Active, with `capture.logs` on, Firewatch makes the default a `firewatch` stack of Nightwatch's `nightwatch` channel and your original default, so your logging keeps working as configured. Nightwatch's channel comes first because a handler such as the `null` channel's stops the handlers after it. When the default channel already includes `nightwatch`, directly or in a nested stack, nothing is wrapped, so no log is recorded twice. Logs sent to a named channel, such as `Log::channel('slack')`, are not captured. Nor are logs from a default stack that lists `nightwatch` after a channel that stops the handlers after it. An application channel of its own named `firewatch` is left alone, and then nothing is wrapped. With `capture.logs` off, or in Off, logging is left alone.

Queries carry their bindings, which Nightwatch never records. In Active, Firewatch listens to `QueryExecuted` around Nightwatch's own query listener and gives each query record the values its query sent to the database, as a JSON list in the `queries` view's `bindings` column. A binding set is paired only to the record Nightwatch writes for that very query, and only when its SQL and connection still match, so a query Nightwatch never records, because it was ignored, rejected or paused, lends its bindings to no other. A query record without a certain pair, such as one whose SQL a `redactQueries()` callback changed, has `bindings` NULL. Bindings are stored raw, as a list in the order the query was given them, named bindings included: a string is cut to 1,024 bytes with the truncation marker, one that is not UTF-8 reads `[binary N bytes]`, an infinite or NaN float is stored as its string (`INF`, `NAN`), a stringable value as its string and any other value, such as an array or an object, as its type in brackets (`[array]`). A query whose bindings can't be read, and every query while Nightwatch's provider was registered before Firewatch's, has `bindings` NULL. A query's bindings keep up to 16,384 bytes of JSON, and the ones that don't fit are replaced by one `... [N more bindings]` element.

Redaction is relaxed, because the store never leaves your machine and the redacted value is usually the answer. In Active, Nightwatch's built-in lists are off, so payload fields such as `password` and headers such as `Authorization` and `Cookie` are stored as sent. List payload fields in `capture.redact_payload_fields` to replace their string values, matched by exact key at any depth, and headers in `capture.redact_headers`, matched in any case. A replaced value reads `[N bytes redacted]`, `Authorization` keeps a registered scheme (`Bearer [N bytes redacted]`) and `Cookie` keeps each cookie's name. Header redaction runs before your own `Nightwatch::redactRequests()` callbacks, which still apply, as do every other `redact*` callback. Firewatch never redacts URL query strings, SQL, log text, exception messages or the Context. The `php-auth-*` headers are never stored, and userinfo is stripped from outgoing request URLs. Payloads are kept for responses with status 500, while `capture.request_payload` is on.

In Active and Off, `NIGHTWATCH_ENABLED`, `NIGHTWATCH_TOKEN` and the `NIGHTWATCH_INGEST_*` variables have no effect. In Active, neither have the `NIGHTWATCH_*_SAMPLE_RATE`, `NIGHTWATCH_IGNORE_*`, `NIGHTWATCH_LOG_LEVEL`, `NIGHTWATCH_CAPTURE_EXCEPTION_SOURCE_CODE`, `NIGHTWATCH_CAPTURE_REQUEST_PAYLOAD`, `NIGHTWATCH_REDACT_PAYLOAD_FIELDS` and `NIGHTWATCH_REDACT_HEADERS` variables, nor `NIGHTWATCH_DEPLOY` while `deploy` is set. Queue workers, Octane and Horizon read the mode at boot, so restart them after changing it.

## Configuration

Every key except `budgets` can be set from an environment variable, so publishing the file is optional:

```bash
php artisan vendor:publish --tag=firewatch-config
```

| Key | Environment variable | Default | Accepted values |
|---|---|---|---|
| `enabled` | `FIREWATCH_ENABLED` | `true` | `true`, `false`, `1`, `0`, `yes`, `no`, `on`, `off` |
| `environments` | `FIREWATCH_ENVIRONMENTS` | `local,testing` | names of letters, digits, `_`, `.` and `-`, comma-separated or a list |
| `database` | `FIREWATCH_DATABASE` | `storage/firewatch/firewatch.sqlite` | a file path outside `public/`; relative paths resolve against the base path |
| `busy_timeout` | `FIREWATCH_BUSY_TIMEOUT` | `300` | milliseconds, 0 to 5000 |
| `retention.age` | `FIREWATCH_RETENTION_AGE` | `7d` | digits then `s`, `m`, `h`, `d` or `w` |
| `retention.records` | `FIREWATCH_RETENTION_RECORDS` | `100000` | 1 to 10000000 |
| `deploy` | `FIREWATCH_DEPLOY` | unset | any string, cut at 255 bytes |
| `capture.logs` | `FIREWATCH_CAPTURE_LOGS` | `true` | a boolean |
| `capture.request_payload` | `FIREWATCH_CAPTURE_REQUEST_PAYLOAD` | `true` | a boolean |
| `capture.redact_payload_fields` | `FIREWATCH_REDACT_PAYLOAD_FIELDS` | none | comma-separated or a list |
| `capture.redact_headers` | `FIREWATCH_REDACT_HEADERS` | none | comma-separated or a list |
| `budgets` | none | none | a list of budget entries |

An invalid value never stops capture: that key alone falls back to its default, and console commands report the problem once.

On SQLite releases with the WAL-reset bug (3.7.0 to before 3.44.6, 3.45.0 to before 3.50.7, and 3.51.0 to before 3.51.3), every write is serialized through an exclusive lock on `firewatch.sqlite.lock` beside the store, created `0600` when Firewatch creates it. The lock is polled every 5 ms within `busy_timeout`, the write gets what is left of it, and the connection is opened and closed inside the lock for each batch. A batch that can't take the lock in time is dropped as `busy`. On other releases no lock file is taken and one connection is kept per process.

Firewatch keeps one writer connection per process on SQLite releases without the bug, and stops using it once it can no longer be trusted. After a fork, the child opens its own connection and holds the inherited one unused until the child exits, rather than closing it from the child. On every batch the writer compares the store file's device and inode with the ones it opened; a store that was deleted is recreated lazily under the usual rules, and one that was replaced is opened again, after the old connection is closed. Closing the old connection removes the `-wal` and `-shm` files beside the store by name, so deleting or replacing the file while other processes still hold it open, and leaving a stale `-wal` or `-shm` beside a replacement, remain the caller's to avoid. Reads open the store afresh each time, so they always read what is there.

After each batch is committed, the writer that stored it prunes, at most once a minute across all processes: a process claims the pass by advancing `prune_claimed_at` in `meta`, and only one of two racing processes wins. A batch that failed starts no pass, and a step that finds the store busy stops silently. A pass removes records older than `retention.age` by event time (`started_at`), oldest first, in chunks of 2,000 rows and at most 20 chunks per pass; the rest waits for the next pass. When the store holds more than `retention.records`, a pass trims it to 90% of that cap, again oldest first. Users and drift age out by `last_seen`. Each chunk's delete commits together with its coverage marker: `pruned_through` in `meta` is the newest `started_at` removed and never decreases, `pruned_by` is `age` or `cap`, and answers state the per-type coverage start and reason from them.

A size backstop sits behind age and count as a safety net, not a setting: when the store's live bytes, `(page_count - freelist_count) * 4096`, pass 512 MiB, the same pass deletes the oldest records, in the same chunks and within the same 20 transactions, until they are at most 90% of that, reading the page counts again after each chunk; the marker's `pruned_by` is then `size`. Every connection also holds the file to 125% of it, 640 MiB, so a burst between two passes still lands, while a sustained flood beyond that is dropped as `full` in `failures.jsonl`. Freed pages are returned to the file in small steps: a pass that deleted, or that finds more than 1,024 free pages, runs an incremental vacuum of 1,024 pages (4 MiB), and a pass that deleted then runs a passive checkpoint and `PRAGMA optimize`, each best effort. The backstop appears in no setting and in no answer.

`php artisan firewatch:clear` removes every record, user and failure line from the store, or with `--type=<type>` the records of one of the twelve types (`user` and anything else is refused, listing them), after a confirmation that defaults to no; `--force` skips it, and `--no-interaction` without `--force` aborts. It never creates a store: with none, or an empty file, it prints `Nothing to clear.` and exits 0, and a store of another schema, a damaged one, a file that is not Firewatch's or a SQLite below the minimum is refused with a message and exit 1, untouched. It writes its marker first, in a transaction of its own that also reads the newest id: `cleared_at` for a full clear, or that type's entry of `cleared_types`, which only move forward, so a reader that sees a half-cleared store already clips its history. It then deletes up to that id in chunks of 2,000, so records that arrive meanwhile stay, and ids carry on where they were. A full clear also deletes the users last seen up to its start and empties `failures.jsonl`; drift, the other `meta` keys and the id sequence are kept, and a clear of one type touches nothing else, not even records of unknown start. Freed pages are returned to the file and the log truncated; a reader that keeps the log from truncating is reported, not an error. It waits 5 seconds for a busy store, whatever `busy_timeout` is, then prints `The store is busy; try again.` and exits 1. `--drop` rebuilds the store in place instead, as the way out of a schema mismatch or a damaged file: after a confirmation that defaults to no (`Continue?` names the path and that diagnostics go too), it drops every table and view and builds the current schema, so ids restart at 1, drift and `meta` start over (`created_at` is new, and no clear marker is kept), then vacuums, truncates the log and empties `failures.jsonl`. The file is never unlinked, so a process holding it keeps working. A store of another schema is rebuilt with `rebuilt_why` `schema`; a damaged one is moved to `firewatch.sqlite.corrupt` (with its `-wal` and `-shm`, replacing an earlier copy), a new store is created with `rebuilt_why` `corrupt`, and the output says so instead of printing sizes. It can't be combined with `--type`, never touches a file that is not Firewatch's, and with no store prints `Nothing to clear.`. It runs while Firewatch is off, and does not exist where Firewatch is stepped aside.

A store of another schema version, older or newer, is rebuilt in place by the next writer, never migrated: inside one `BEGIN IMMEDIATE` it reads the stamps again, in case another writer rebuilt first, drops every view and table, creates the schema and stamps it, and the batch is stored in the new store. The records are gone, and the file is never unlinked, renamed or replaced, so processes that hold it open stay valid. A Firewatch file that SQLite reports as damaged is moved aside, with its `-wal` and `-shm`, as `firewatch.sqlite.corrupt`, `firewatch.sqlite-wal.corrupt` and `firewatch.sqlite-shm.corrupt`, replacing the copies of an earlier recovery, and the batch is stored in a new store; the recovery adds a `corrupt` line to `failures.jsonl` with `dropped` 0, and is not reported. A file is Firewatch's when its header, read as raw bytes, starts with SQLite's magic and carries Firewatch's application id at offset 68. A store that young may still show 0 there until its write-ahead log is first checkpointed, and a damaged one is then treated as not Firewatch's and left alone. A file that is not Firewatch's, another application's SQLite file or one that is no SQLite file at all, damaged or not, is never written to, moved or dropped into: every batch for it is dropped as `foreign`, and `database` should point elsewhere. A zero-byte file counts as a new store.

Reading never repairs. `overview` reports a store it can't read as usual by one of six states: absent (no file, a zero-byte file, or a database nothing was ever written to) answers that no store has been written yet; a file that is not Firewatch's, a store of another schema version (the next captured batch rebuilds it), SQLite older than 3.38.0, a damaged store (the next captured batch replaces it) and a store that stays busy for 1000 ms each answer that the store is unusable, with the reason.

`rank` lists the groups of one `type` worst first by a measure `by`, over `since` and `until`, restricted to an exact `deploy` if given; `limit` is 1 to 100, default 20. `type` is required and is one of the eleven types that have groups (the hyphenated wire names, matched exactly; `log` has none). `by` is `p95_duration` (the default, `occurrences` for `exception`), `p50_duration`, `max_duration`, `total_duration`, `occurrences`, `p95_memory`, `max_memory`, `last_seen` or `queries`; an exception has no duration, and memory and `queries` fit only the four execution types (request, command, job-attempt, scheduled-task), so any other pairing is refused with `invalid_argument` listing what fits. Percentiles are nearest rank over the observed values, sorted by value and then id: the value at rank `max(1, ceil(n * p / 100))`, never interpolated. A median needs 3 records and a 95th percentile 20; below that the value is `null` and the row's `withheld` names it with `reason: sample_too_small`, `have` and `needed`, and a group with fewer than 3 records lists its raw values in `values_ms`. Occurrences, min, average, max and total are always shown. A record without a duration (and a skipped scheduled task, which never ran) counts in `occurrences` and is left out of the duration statistics, which a note states. Rows with no value for the measure sort after the others, and ties go to the group with more records, then to the lower hash. When no group at all has enough records for the percentile, the order falls back to the maximum of the same quantity and a note says `No group has enough records for p95 (needed 20); ordered by max.` Each row has the group id, its label (the display field of its latest record in the window: `route_path` for a request, with `(no route matched)` when empty, `name` for a command, job attempt, scheduled task or queued job, `sql`, `host`, `key` or `class`), the `method` of a request or outgoing request, the statistics in `_ms` (2 decimals), peak memory in `_mb` (1 decimal) and the summed `queries` counter for executions, `failure_pct`, `first_seen_at` (the group's earliest stored record, whatever the window), `last_seen_at` (in the window), the number of distinct `deploys` in the window and `slowest_execution_id`. `failure_pct` is the share of records that failed among those that have the field judged, to one decimal: a status of 400 or more for a request or outgoing request, a non-zero exit code for a command, `failed` or `released` for a job attempt, `failed` (not `skipped`) for a scheduled task; every other type shows `null`, never 0. The result also counts the records of the type in the window, the groups ranked and the records without a group. Groups of the same label and different hashes stay separate rows. Matching on a label, a per-deploy breakdown, cursors and budget verdicts are not part of it yet.

`occurrences` lists individual records, newest first, for at least one selector (`group`, `type`, `execution_id`, `trace_id`, `job_id` or `user_id`), with filters for the types they fit (`method`, `status`, `outcome`, `level`, `slower_than_ms`, `at_or_above`, `matching`) and `order` by `recent`, `slowest`, `memory` or `queries`; each row names its group and carries a `detail` object.

`busy_timeout` bounds only the capture side: a batch that can't be written within it is dropped rather than stalling the request, and `0` drops it at once. A batch that can't be stored, because the store is busy past `busy_timeout`, full or not a Firewatch store at all, is dropped, never retried or thrown into your application. Each dropped batch adds one line to `failures.jsonl` beside the store, unless the store's directory is missing or another process holds the file's lock: `at` (Unix seconds), `kind` (`busy`, `full`, `corrupt` for a damaged store that was replaced, `foreign` for a file that is not a Firewatch store, `io` for a filesystem error, or `other`), `code` (the SQLite result code, or null), `message` and `dropped` (its record count). The file keeps the latest 100 lines, so older drops are no longer counted there. A process reports its first dropped batch through the exception handler, and a failure to write the line or to report is swallowed.

Give each store its own directory: two stores in one directory would share their companion files. The first captured batch creates the directory, readable only by its owner, with a `.gitignore` that keeps it out of commits, and the store file inside it, also readable only by its owner. Reading never creates anything. The store is a plain SQLite file, not a Laravel database connection, so capturing it records none of its own queries.

Every record lands in one `records` table under Nightwatch's own field names, with its type-specific fields in a JSON `data` column. Twelve views read it per type (`requests`, `commands`, `job_attempts`, `scheduled_tasks`, `queries`, `exceptions`, `logs`, `cache_events`, `mail`, `notifications`, `outgoing_requests` and `queued_jobs`), with each field as its own column. A cache event's kind is `event` rather than the wire's `type`, and `started_at` is when a record started: mail, notifications and queued jobs, which Nightwatch stamps when they end, start one duration earlier.

Signed-in users are not records. Each one Nightwatch sees is kept once in a `users` table with its `id`, `name`, `username`, when it was `first_seen` and when it was `last_seen`; a later sighting updates everything but `first_seen`. A user record without an id stays in `records` instead.

Nothing Nightwatch sends is dropped. Every difference from the fields and types Firewatch was built against is counted in a `drift` table by `kind`, record `type`, version `v` and `detail`, with how often and when it was first and last seen: a record of an unknown type (`unknown_type`) or version (`unknown_version`), a field Firewatch doesn't know (`unknown_field`, kept in `data`) or that is missing (`missing_field`, stored as NULL), a field of an unexpected type (`structure`, stored as sent), each batch captured with a Nightwatch release off the verified 1.30 line (`version`), and a process's first batch when Nightwatch's provider was registered before Firewatch's (`structure`, detail `provider order`). Input that can't be read as a record, such as one that isn't an object, has no string `t` or can't be encoded, is kept as a `records` row holding only its `type` and an `error` in `data`, and counted as `structure`. The table keeps at most 500 rows; new drift beyond that is added to one `... [overflow]` row per kind. A `meta` table keeps the Nightwatch release of the latest batch and whether it is verified.

Long values are cut, never dropped. A string over 65,535 bytes, in a common column or in `data`, is cut on a UTF-8 character boundary and ends with `... [truncated, N bytes total]`, where N is its original length; the marker counts toward the 65,535 bytes. Fields Nightwatch sends as JSON strings (the exception `trace`, request `headers` and `payload`, `context` and `extra`) are kept whole, including one Nightwatch already cut mid-value. When a record's `data` is still over 1 MiB, its largest strings are cut to 4,096 bytes, largest first, until it fits, and then the code snippets in an exception's trace frames are set to null. A record still over 1 MiB after that is kept as it is. Nightwatch cuts some fields at 65,535 bytes itself without a marker (log and exception messages, outgoing request URLs); those arrive at the limit and are kept as sent, unless its cut split a character, whose replacement pushes them over and gets them the marker.

A budget entry names an execution type (`request`, `command`, `job-attempt` or `scheduled-task`), optional matchers (`methods` and `path` for requests, `name` otherwise) and a `duration` ceiling in milliseconds, a `memory` ceiling in MB, or both:

```php
'budgets' => [
    ['type' => 'request', 'methods' => ['POST'], 'path' => 'checkout/*', 'duration' => 800, 'memory' => 64],
    ['type' => 'request', 'duration' => 300, 'memory' => 32],
    ['type' => 'command', 'name' => 'reports:*', 'duration' => 60000],
    ['type' => 'scheduled-task', 'duration' => 5000],
],
```
