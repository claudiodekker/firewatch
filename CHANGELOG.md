# Changelog

## Unreleased

### Added

- Firewatch installs as a dev dependency and registers Nightwatch's provider and `Nightwatch` facade alias itself; Nightwatch is excluded from package discovery.
- An optional `config/firewatch.php`, published with `vendor:publish --tag=firewatch-config`, with twelve keys; every key except `budgets` can be set from a `FIREWATCH_*` environment variable.
- An invalid configuration value falls back to its default alone and is reported once per console process; web processes stay silent.
- Firewatch resolves one mode per process at registration: stepped aside outside `environments`, Off in a `firewatch:` command, when disabled or without a usable SQLite, and Active otherwise. Each mode writes only its own Nightwatch keys, so `NIGHTWATCH_ENABLED`, `NIGHTWATCH_TOKEN` and `NIGHTWATCH_INGEST_*` have no effect in Active and Off.
- A console process in a disallowed environment reports once that Firewatch is stepped aside. The `firewatch:server`, `firewatch:doctor` and `firewatch:clear` commands (the last two stubs for now) and the publish tag exist only in Active and Off, and configuration issues are reported only there.
- In Active and Off, Nightwatch's ingest is swapped for Firewatch's, after checking by reflection that its interface and property are unchanged; otherwise a console process reports it once and Nightwatch keeps its own ingest, disabled in Off and behind the dead token and address in Active. Neither of Firewatch's ingests sends anything.
- In Active, Firewatch's ingest writes every batch the sensors record into the store, in one transaction and in the order they were recorded; a batch it can't store is reported and never fails the application. The first batch creates the store's directory as `0700` with its own `.gitignore`, and the file as `0600`. In Off it stores nothing.
- Every record type is mapped through one contract table into the store's common columns and its `data`, and read through one view per type with its fields as columns. A job attempt's `attempt_id` becomes its `execution_id`, a fatal error without an execution takes its trace unless it ended a job, mail, notifications and queued jobs start one duration before Nightwatch's timestamp, and JSON-string fields are stored decoded unless they aren't JSON.
- Signed-in users go to a `users` directory instead of `records`: a user is added with the instant it was first seen, and each later sighting updates its name, username and last-seen instant. A user record without an id is kept as a record, and directory entries never count as records.
- Every difference between what Nightwatch sends and the contract table is counted in a `drift` table, per batch and in its transaction, by kind (`unknown_type`, `unknown_version`, `unknown_field`, `missing_field`, `structure` or `version`), type, version and detail, and nothing is dropped. The contract table now lists each field's accepted JSON types. Input that can't be read as a record is stored as an error placeholder, a timestamp that isn't a number starts the record at NULL, and a batch from an unverified Nightwatch release counts one `version` drift. The table keeps at most 500 rows, folding new drift beyond that into one overflow row per kind, and a `meta` table keeps the latest batch's Nightwatch release and whether it is verified. The first batch of a process whose Nightwatch provider registered first counts a `provider order` drift.
- In Active, a listener on Nightwatch's `IngestingEvents` vetoes every batch, so Nightwatch's own ingest transmits nothing even when it could not be swapped.
- A console process in Active or Off reports once when Nightwatch's provider was registered before Firewatch's, naming the fix; in Active it also reports once when the `IngestingEvents` event is missing. Neither disables anything.
- `php artisan firewatch:server` runs the `firewatch` MCP server over stdio with the tools capability only, and exits when its input ends. It touches nothing in the store at boot, forces `app.debug` off and shortest round-trip floats, and sends PHP errors and anything printed outside the protocol, such as a provider's output at boot, to stderr. No laravel/mcp handle is registered, so `mcp:start` has nothing to run.
- The first tool, `overview`, answers with the store clock that no store has been written yet, that the store holds no records, or how many requests it holds, read in one snapshot.
- `overview` takes `since` and `until`, read with a strict time grammar (epoch seconds up to 4102444800, ISO 8601, local date-time or date, relative such as `-1d`, `now`) in the application timezone against the store clock. The window is half-open on `started_at`; `yesterday`, millisecond epochs and other free-form input fail with `unreadable_time`, and `since` not before `until` fails with `empty_window`. A window without records answers `window_empty`.
- A failed tool call is a plain-text error with one of nine closed codes (`missing_argument`, `invalid_argument`, `conflicting_arguments`, `unreadable_time`, `empty_window`, `split_outside_window`, `not_found`, `bad_cursor`, `internal`), the argument, what is accepted and a valid example. An unknown or misspelled argument is `invalid_argument` and an argument of another tool `conflicting_arguments`, both listing what the tool takes, before the store is read. `format` is now matched exactly, not trimmed or lowercased. An unexpected exception becomes `internal`, even with `app.debug` on, and is reported once.
- Every answer's `coverage` also carries `types_read`, `history` (`from`, `reason`, `retention`) and `straddling`, and the Store line says from when the history is complete. The store stamps its creation in `meta` when its schema is created, so a store rebuilt gets a new start. Every answer carries the structural blind spots of the record types it read, even when it is empty, from a closed catalogue of eighteen ids with one pinned sentence each; `overview` reads all twelve types.
- Answers are bounded: a reader fetches one row beyond the limit so exactly `limit` rows is complete, a cell is cut at 2,000 characters with `... [truncated, N characters]`, and an answer over 24,000 characters (8,000 tokens) drops whole rows from the tail of its lowest-priority list, never the first row of the first list, the summary, the blind spots or the next calls. Every cut is a `truncated` entry with reason `limit`, `cap` or `size` and how to get the rest.
- `firewatch:server --list` prints the tool listing without a session, and `--list --json` prints it as JSON; `--json` alone exits 1.
- In Active, Nightwatch's sample rates are forced to 1, its `ignore_*` filters off and its log level to `debug`, so every execution is captured; `Nightwatch::ignore()`, `pause()`, `dontSample()`, `Sample` rates on routes and scheduled tasks and `reject*` callbacks still drop what they target. Exception source lines are always captured, and `deploy`, when set, is written as Nightwatch's deployment.
- Strings over 65,535 bytes are cut on a UTF-8 boundary with a `... [truncated, N bytes total]` marker, and a record's `data` over 1 MiB has its largest strings cut to 4,096 bytes and then its trace code snippets nulled. JSON-string fields are kept whole, and no record is dropped for size.
- In Active, Nightwatch's built-in redaction lists are off, so payloads and headers are stored as sent. `capture.redact_payload_fields` and `capture.redact_headers` redact to `[N bytes redacted]`, keeping `Authorization`'s scheme and `Cookie`'s names, and header redaction runs before the application's `redactRequests` callbacks. `capture.request_payload` now turns Nightwatch's payload capture on or off.
- In Active, with `capture.logs` on, the default log channel is wrapped in a `firewatch` stack with Nightwatch's channel first, so every default-channel log is captured without changing `LOG_STACK`. A default that already includes `nightwatch`, followed through nested stacks, is left as it is.
- In Active, each query record carries the bindings its query sent, in a `bindings` column on the `queries` view, paired only when the record's SQL and connection match its own query and NULL otherwise. Strings are cut to 1,024 bytes, binary strings read `[binary N bytes]`, and a query's bindings are capped at 16,384 bytes of JSON with the rest counted as `... [N more bindings]`.
- A batch that can't be stored is dropped and recorded as one line in `failures.jsonl` beside the store, with `at`, `kind` (from the SQLite result code, `foreign` for a file that is not a Firewatch store, `io` for a filesystem error), `code`, `message` and `dropped`, keeping the latest 100 lines. Only the process's first dropped batch is reported, and a failure of either step is swallowed.
- On SQLite releases with the WAL-reset bug, every write holds an exclusive lock on `firewatch.sqlite.lock`, polled every 5 ms within `busy_timeout`, and opens and closes its connection inside it; a batch that can't take the lock in time is dropped as `busy`.
- On SQLite releases without the WAL-reset bug, the writer's connection is keyed by process id and held unused until the child exits after a fork, and every batch compares the store file's device and inode with the ones it opened, closing and reopening the connection, and recreating the store when it is gone, after the file was deleted or replaced.
- A store of another schema version, older or newer, is rebuilt in place by the next writer inside one `BEGIN IMMEDIATE`, without unlinking the file, and the batch lands in the new store. A damaged Firewatch file is moved aside with its `-wal` and `-shm` as `*.corrupt`, keeping one copy, and the batch lands in a new store; the recovery is one `corrupt` line in `failures.jsonl` with `dropped` 0. A file that is not Firewatch's, a foreign SQLite file or one that is not SQLite, is never written to or moved, and a zero-byte file is a new store.
- `overview` now says why a store can't be read: a file that is not a Firewatch store, a store of another schema version, SQLite older than 3.38.0, a damaged store or a store that stays busy for 1000 ms each give an unusable-store answer with the reason, and an absent or zero-byte store gives the no-store answer.
- Every tool answers with one fixed envelope (`tool`, `now`, `window`, `summary`, `empty`, `result`, `coverage`, `blind_spots`, `notes`, `truncated`, `next`) in markdown, or in JSON with `format: json` as structured content beside the same compact JSON as text; a `format` that is neither is refused. Markdown follows one layout and set of cell rules, and empty answers name their kind (`no_store`, `store_unusable`, `store_empty`, `window_empty`, `no_match`) with the records they were drawn from. `overview` now reports its record count and the store's span.
